How History works

What is History?

Every IFC file in the project lives in its own git repository. Each approved Modify proposal becomes one commit that carries the request, the number of targets and the generated code in its body. History lists those commits per file, newest first, so you can see what changed, when, by whom, and go back to any earlier state.

Lifecycle of a commit

CURRENT HEADThe newest commit; the file on disk is this state.
[MODIFY]An approved proposal: the reviewed copy replaced the original and was committed with the code.
RESTORE POINTA restore: a new commit that makes the file look like an earlier one. Nothing is rewritten or lost.
SupersededA commit a later restore stepped over; still restorable itself.

How to read a commit and restore one

Diff opens the change as the card showed it: one row per property, attribute or entity, aggregated with a count; a marks a row that was flagged and acknowledged at approval.
Targets badge is how many entities the generated select() returned; modified / added / removed are the diff's counts over real entities (property sets and relationships never count).
Restore reverts the file to that commit's state, creates a new commit for it, and re-parses the file into the database so Ask, Explore and the conflict scan see the restored values. Confirm the dialog; the restore takes as long as a reprocess.
Restored links a commit to the restore that brought it back; hash links jump between the two.

Who can do what

  • Every member of the project, viewers included, can read History and open a diff.
  • Only the project owner can restore; editors approve changes on the Modify tab but do not rewind the file.

Caveats

A restore is a new commit on top, never a rewrite: the history stays complete and every state stays restorable. Restoring re-parses the whole file, so it can take a minute on a large model; embeddings are regenerated as part of that reprocess. A pending proposal made against the file before a restore will be refused at approval ("file changed, please re-propose") because its fingerprint no longer matches. Commits made by earlier versions of Castor show the diff in their own, older format, or none. History is per file: uploading a new file starts a new section, it does not continue the old one.
