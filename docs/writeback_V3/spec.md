# Writeback V3 — Specification

**Status:** built 2026-09-15. Decided 2026-09-14 (brainstorm frozen at v3.2) and revised twice
the same day: once after a design review against the Zen of Python (decision log, entries marked
*review*) and once after a code-grounded review that checked every "kept" and "existing" claim
against `src/` (*review 2*). Built on 2026-09-15 (*build*) and revised the same day after three
code reviews of the built pipeline (*review 3*, *review 4*, *review 5*): the approval chain, the
snapshot's coverage of type objects, the index refresh and the benchmark's scoring rules changed;
the affected rows say so. G-1 and V-3 were revised once more after the first live door case
(*review 6*: not-yet-set standard properties in grounding, the property name in the flag rule).
Every requirement is `built` (code and unit tests pass); `verified` markers point at the bake-off
record as its rows land.
**Scope:** the Modify pipeline from user message to git commit, its UI card, its settings, and the
benchmark that proves it. Ask, Explore, the conflict scan and Facilities are out of scope.
**How to read:** each requirement has a behaviour, the deterministic check behind it, an
acceptance criterion, what proves it, and a status marker (`target` / `built` / `verified`, see
[README](README.md)). The "proven by" column is the only place in this folder that names code.

Prefixes: **G** ground · **C** generate · **R** run · **V** verify · **A** approve · **U** card and
settings · **B** benchmark · **P** performance.

The shape, in one line: `ground → generate → run → verify → (human) → approve`. Two model calls
per request without repairs: one writes the code (at most two more if a repair is needed, C-4),
one explains the diff. Guardian is a third, optional, at proposal time, so its verdict is on the
card before the human decides; its document search costs one embedding call besides. A request
the model declines (C-6) costs one call.

## C — Generate (model call 1)

| ID | Behaviour | Check | Acceptance | Proven by | Status |
|---|---|---|---|---|---|
| C-1 | One call returns **one fenced Python block** defining `select(model) -> list` and `modify(model, targets) -> None`. The block is extracted by regex; the output is not JSON and no Ollama `format=` is used | extractor | a response without both functions is a repair (C-4), not a crash | extractor unit test | built |
| C-2 | Helper library `castor_select`: eight read-only names (elements_in_storey, elements_in_space, by_type, by_name, by_pset_value, by_material, decomposition_of, container_of), each a wrapper of at most five lines over `ifcopenshell.util.element` (`util.selector` is whitelisted for raw code; no helper uses it). The storey and space helpers return elements only: no spaces, no openings or other feature elements. The first docstring line of each helper is rendered into the prompt verbatim, so it must say exactly what the helper does. Raw ifcopenshell is always allowed; the prompt shows one mixed example, written in the sheet's notation (*review 6*), whose pset recipe is `pset.add_pset` (find-or-create by name), `pset.unshare_pset` when that pset is attached to other entities too (*review 5*: `add_pset` returns a shared pset as is, and an edit on it lands on every entity sharing it), then `pset.edit_pset`, never a pset reached through the type object. Creation has a recipe with placeholders (*review 6*): `select()` returns the project (or the storey a new space belongs to), `modify()` calls `root.create_entity(ifc_class=..., name=...)`, a space goes under its storey with `aggregate.assign_object`, elements into a zone with `group.assign_group`; the decline rule reads "names nothing to change or create", so a creation is never refused for naming no target. The growth rule lives in the module docstring: add a helper only when a benchmark case fails on the raw traversal twice | — | every helper has a unit test against the sample house | helper test module | built |
| C-3 | `modify` receives `select`'s result and may **narrow** it (by type or name for multi-intent requests) but never widen it. Enforced by V-1, not by prompt wording | diff scope | a modify iterating `model.by_type` instead of `targets` is caught by V-1 | benchmark integrity | built |
| C-4 | **One repair rule.** Every check after generation yields either nothing or one error string: extraction failure, traceback, zero targets, scope violation. The repair prompt is the previous code plus that string; the grounding lists are already in the prompt, so no failure kind gets a special prompt. At most two repairs per request; a third failure ends in a visible rejection quoting the last error. A model that does not answer within the wall-clock cap (240 s for the code call, 90 s for the explainer and for Guardian; each call also carries a token cap, `num_predict` 1536 for code and 160 for the sentence), or a provider that cannot be reached, is not a repair: it ends the request at once with a retryable failure card | repair counter | a request whose code fails three times ends in a rejection, not a loop; zero targets three times ends in a rejection whose text is the zero-target error; a timeout is one visible failure, never a 500 | unit test with a canned model | built |
| C-5 | Multi-intent requests are one code block, one diff, one commit | — | the two-property corpus cases produce one proposal | benchmark | built |
| C-6 | **A `REJECT:` line is a first-class answer** (*build*). A greeting, a question, a geometry request or a request that names nothing to change or create ends in one call with the model's reason, shown as "Declined: …" with a failure record. It is not a failure kind: no repair, no proposal row. The benchmark's reject column measures over-refusal as well as under-refusal (B-2) | extractor | a greeting ends in one model call and no proposal; a change case the model declines scores false on targets and diff match | generator unit test; benchmark | built |

## R — Run (no model call)

| ID | Behaviour | Check | Acceptance | Proven by | Status |
|---|---|---|---|---|---|
| R-1 | One child process per attempt, same protocol as today (job on stdin, result in a file). The child: opens the scratch copy → snapshots the open model (one property pass, not a second file open) → execs the block → `targets = select(model)` → `modify(model, targets)` → snapshots again → diffs → writes the scratch copy → returns `{targets, diff}`. A `select` that returns one entity instead of a list is taken as a list of one. With zero targets the child skips `modify`, the second snapshot and the write. There is no self-reported change list; the result-schema check is removed. "Read-only select" means select runs before modify on a copy the diff inspects; no flag, no api patching | result file shape | the result carries `diff.as_dict()` and the target GlobalIds; a select that mutates shows up in the diff | sandbox test | built |
| R-2 | The scratch copy is **kept** for the proposal's lifetime at `.<stem>.proposal-<uuid8>.ifc` beside the original (a short token minted before the row exists and stored on the row, *build*). Apply, reject and supersede each delete it in the same call; supersede is the existing pending-sweep that already runs on every new proposal. A cancellation (the user pressed Stop, or the tab closed) at any point after the copy is made deletes it; a cancellation after the row exists but before it is linked to its message rejects the row, because nothing could ever supersede it. A management command (`sweep_scratch_files`) deletes scratch files whose proposal is no longer pending or claimed, for crashes only | — | after propose the scratch exists; after each terminal status it does not; after a cancel no scratch and no pending row remain | executor test; pipeline and proposal tests; sweep test | built |
| R-3 | Forbidden-pattern scan, restricted builtins and imports, and the wall-clock timeout are kept as they are, with one addition to the import whitelist: `castor_select`, two additions to the builtins: `getattr` and `hasattr` (attribute access is unrestricted anyway and both are ordinary idioms; *review 4*), and one change to the timeout: it grows with the file (a base budget plus a per-MiB share), because the child also opens, snapshots twice and writes the copy. The helper module lives in `ifc_processor/services/` and imports nothing from Django, because the sandbox child runs without Django. *Review 6*: the child also binds the api modules the sheet names (`code_sandbox.API_MODULES`) as model-bound proxies once the copy is open, so a call copied from the sheet runs without an import or a model argument (the model passed explicitly is dropped; `type` doubles as the builtin); `model.create_entity` is a forbidden pattern whose text names `root.create_entity`, because a raw entity has no GlobalId and the diff cannot see it; a local variable shadowing an api module (`pset = pset.add_pset(...)`) gets an error that says so | — | existing sandbox tests pass; a select that imports `castor_select` runs; a select that imports `django` does not; the budget for a 10 MiB file is larger than for a 1 MiB file; `root.create_entity(ifc_class="IfcZone", name=...)` from a project selection yields one added object; `type(x)` still works; `model.create_entity` is refused before spawning | existing tests; sandbox tests | built |

## V — Verify (deterministic first, one advisory model call last)

| ID | Behaviour | Check | Acceptance | Proven by | Status |
|---|---|---|---|---|---|

## A — Approve and execute

| ID | Behaviour | Check | Acceptance | Proven by | Status |
|---|---|---|---|---|---|
| A-1 | **The proposal row is the journal.** Eight new, explicit columns: `code`, `target_global_ids` (JSON list), `diff` (JSON, `IfcDiff.as_dict()`), `base_fingerprint`, `scratch_path`, `guardian_skipped`, `flags_acknowledged_at`, `explainer_model` (added in the build so the card can name the model, U-1). No V2 column is reused with a new meaning: `changes` (a list-defaulted JSON field holding a journal dict), `diff_preview` (text holding JSON), `code_review_acknowledged_*` and `confidence` (documented 0–1, stores 80) all keep their V2 semantics and become nullable in the same migration; history rows keep rendering. One property, `has_flagged_rows`, computed from the stored diff and the request, replaces `requires_code_ack` | — | a proposal cannot be approved without code, targets, diff, fingerprint and scratch path | migration; model test | built |
| A-2 | Fingerprint mismatch at approval **aborts** with "file changed, please re-propose". There is no warn policy | fingerprint compare | approving after the file changed refuses | executor test | built |
| A-3 | Approval is: fingerprint check → git snapshot of the original if it has no commit yet → `os.replace(scratch, original)` → git commit with the code in the commit body → index refresh of the diff's touched GlobalIds. **The code is not run again.** The approved diff is the applied diff by construction. The git commit method changes signature to take a subject and a body (today it hard-codes a tier label and a fixed body, and its three callers pass a tier). The commit's added and removed counts, and the refresh, are over **objects only**: the property sets and relationship entities a change creates are never counted as entities and never written to the index. The index refresh is the V2 single-open routine promoted from a private method on the execution service to a public function in `ifc_processor`; it opens the file once at approval, writes only classes a full parse would index, links the direct spatial container, and, as in V2, does not regenerate embeddings. A touched type object refreshes its `IFCElementType` row and every occurrence of the type, because occurrences index the values they inherit (*review 4*). Approvals on one file are serialised: the file row and the proposal row are locked from the fingerprint check through the commit, and the status is read from the locked row, never from the caller's instance (*review 4*). A refresh failure is logged, never surfaced as a failed approval: the file and the commit are already in place. Any other failure after the claim marks the row FAILED, deletes the scratch copy and rolls git back to the snapshot (*review 5*). Guardian is not in this chain (A-4) | byte equality | after approval the file is byte-equal to the scratch copy; the index reflects exactly the diff rows and holds no pset or relationship row; the commit body contains the code | integration test | built |
| A-4 | Guardian runs **at proposal time**, as it does today, so its verdict is on the card before the human decides; advice after approval is advice nobody can act on. It is skippable per request, default on, stateless; the skip is recorded (A-1). Its query is built by one function from the dominant aggregated diff row (type, humanised property, new value); the V2 intent-based builder is replaced, not adapted | — | a skipped proposal shows "Guardian skipped" on the card and in history; the query for the fire-rating case reads "wall fire rating EI60" | view + template test; unit test | built |

## Non-goals

- Geometry: any change to placement or representation is a violation, never a feature.
- Multi-file requests.
- A blocking checkpoint between selection and mutation. Revisit only if the bake-off shows a
  material share of runs wasted on wrong selections; the card is the checkpoint.
- An advisory verdict comparing request and explanation. The user compares.
- Re-running the code at approval, and rebasing a proposal onto a changed file. A changed file
  means re-propose.
- Vector matching of storey and space names. Grounding injects the full lists.
- A deterministic sanity check on target type or container. The card shows both.
- A baseline snapshot cache. Revisit only if P-1 shows snapshot time above about two seconds.
- A setting for the explainer model.
- A skill library built from successful runs.
- A constrained api call plan instead of free code: the fallback only if the bake-off shows local
  coders cannot write correct code. The checked-in api sheet (G-2) is needed either way.
